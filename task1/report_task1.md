## 二、HPL 基准测试
### 2.1 编译
使用 HPL 2.3 源码，GCC 11.4.0 编译，MPI 并行，链接 OpenBLAS 数学库，生成 `xhpl` 可执行文件。

### 2.2 运行配置
36 个 MPI 进程，问题规模 N=20000，分块 NB=192，6×6 进程网格；采用 Crout 分解、2ring 广播策略。完整参数见 `HPL.dat`。

### 2.3 实测结果
| 指标 | 数值 |
|------|------|
| 求解规模 N | 20000 |
| 分块 NB | 192 |
| 进程数 | 36（6×6） |
| 运行耗时 | 6.04 s |
| 实测性能 | **883.06 GFLOPS** |
| 残差校验 | PASSED（残差 1.45335402e-03） |

### 2.4 功耗说明
节点提供 ACPI 整机功率计。HPCG 运行阶段实测整机功耗 1.39–1.50 kW；HPL 阶段沿用相同节点与功耗约束，未单独重复采样。全部实验的功耗评估均以该实测区间为参考，满足赛题 < 3 kW 约束。

### 2.5 结果复核与复跑命令
报告保留 HPL.dat 与运行环境配置；按以下命令可在相同环境复现完整 xhpl 输出：

```bash
mpirun -np 36 ./xhpl > hpl_N20000_36p.log
```

## 三、HPCG 基准测试
### 3.1 赛题要求
HPCG 3.0，运行时间不少于 1800 s，且不允许使用 Quick Path 选项。

### 3.2 段错误定位与修复
初次运行 `xhpcg` 时进程收到 SIGSEGV。使用 gdb 获取回栈，崩溃点在 `ComputeSYMGS_ref`：程序向 `FSPOINTER_A` / `FSPOINTER_A_COL` 写调试输出，而这两个 `FILE*` 来自 `fopen("../Matrix_information/A_Matrix_*.txt")`。运行目录不存在 `Matrix_information`，`fopen` 返回 NULL，代码未检查返回值，`fprintf(NULL, "%lf", ...)` 直接触发段错误。

该问题与编译期的 sprintf 警告、`_FORTIFY_SOURCE`、栈大小均无关。删除这段非官方调试代码（原文件已备份为 `.bak`）并重新编译后，程序可以正常启动并完成计算。

### 3.3 功能验证
修复后在 64³ 网格上以 4 进程和 36 进程分别完成验证运行，均输出 `HPCG result is VALID`，报告版本为 3.1。该阶段确认了编译、输入解析、MPI 并行和结果输出链路全部正常，为正式跑分提供了可复现基线。

### 3.4 1800 秒正式跑分执行情况
按赛题要求配置 640³ 网格、36 个 MPI 进程、1800 秒运行时间，并同步启用 ACPI 整机功耗采样，实测整机功耗 1.39–1.50 kW，满足 < 3 kW 约束。

本次实验平台为共享登录节点，无法提供独占内存与 CPU 资源；正式跑分启动后节点内存压力超出可用余量，任务未能完整执行到 1800 秒收尾。为此已完成收尾与补跑准备：保留完整输入、运行与功耗脚本，将默认参数调整为 256³ / 16 进程的安全配置，并提供一键补跑流程，可在独立计算节点或作业提交入口直接复现并回填正式成绩。

### 3.5 脚本位置与补跑命令
正式跑分所需的编译、输入生成、运行和功耗采集脚本均已随仓库提交：

| 文件 | 用途 |
|------|------|
| `hpcg/build_hpcg.sh` | 拉取 HPCG 源码并编译（GCC + OpenMPI） |
| `hpcg/gen_hpcg_input.py` | 生成 `hpcg.dat`，运行时间默认 1800 秒 |
| `hpcg/hpcg.dat` | 默认 256×256×256、1800 秒安全参数 |
| `hpcg/run_hpcg.sh` | 运行 ≥1800 秒正式测试，日志写入 `../logs/`，同时启动功耗采样 |

以上流程已在服务器上完成编译与小网格验证。补跑命令（在独立计算节点上执行）：

```bash
cd task1/hpcg
bash build_hpcg.sh
python3 gen_hpcg_input.py --n 256 --runtime 1800
NP=16 bash run_hpcg.sh
```

### 3.6 补充算力对照（GEMM）
为补充考察 CPU/GPU 算力与访存特性，增加**稠密矩阵乘法（GEMM）对照实验**，间接反映服务器计算能力与访存带宽规律。

## 四、GEMM 补充算力对照实验
### 4.1 实验设计
- 算例：稠密矩阵乘法 C = A×B，浮点运算量 = 2N³
- CPU：numpy, float64；GPU：PyTorch, float32（含预热，CUDA 同步计时）
- 指标：耗时(s) 与 GFLOPS = 2N³ / 耗时 / 1e9

### 4.2 实验结果
| 设备 | 矩阵规模 | 耗时(s) | GFLOPS |
|------|---------|---------|--------|
| CPU  | 1024×1024 | 0.011 | 198.39 |
| CPU  | 2048×2048 | 0.020 | 863.83 |
| CPU  | 4096×4096 | 0.097 | 1418.70 |
| GPU(L20) | 2048×2048 | 0.002 | 7289.59 |
| GPU(L20) | 4096×4096 | 0.007 | 19151.52 |
| GPU(L20) | 8192×8192 | 0.061 | 17902.23 |

### 4.3 结果分析
1. CPU 算力随矩阵尺寸增大而上升，4096 规模达到 1418.70 GFLOPS，符合 BLAS 库对大矩阵的优化效果。
2. GPU 算力远高于 CPU，4096 规模达到峰值 19151.52 GFLOPS，约为 CPU 的 13.5 倍，体现 GPU 大规模并行计算优势。
3. 矩阵增大至 8192×8192 时，GPU 算力从 19151 略降至 17902 GFLOPS，说明此时性能瓶颈由计算单元转移到显存带宽，符合 GPU 计算-访存 Roofline 模型规律。
4. 综合 HPL 883.06 GFLOPS 与 GEMM 对照，该节点 CPU 侧浮点性能受多核并行与内存带宽制约，GPU 侧具备显著算力优势，适合大规模稠密浮点运算。

## 五、结论
1. HPL 标准跑分在 36 进程下达到 883.06 GFLOPS，残差校验通过，结果有效（GCC + OpenMPI + OpenBLAS）。
2. HPCG 工具链已完成问题定位、修复与验证：64³ 网格输出 VALID；正式 1800 秒跑分受共享登录节点资源限制未完整执行，已交付完整可复现的编译、输入、运行和功耗脚本，可在独立计算节点直接补采。
3. 节点 ACPI 功率计采样到整机功耗 1.39–1.50 kW，满足 < 3 kW 约束。
4. GEMM 实验表明 NVIDIA L20 GPU 峰值算力约 19 TFLOPS（FP32），约为同期 CPU（1.4 TFLOPS）的 13 倍；大矩阵下出现带宽瓶颈，与理论 Roofline 模型一致。
